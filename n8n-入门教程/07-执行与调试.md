## 1. 三种执行方式 / Types of Executions

> **官方原文**：An execution is a single run of a workflow.
> **翻译**：执行（Execution）就是工作流的一次运行。

| 类型 | 英文 | 怎么触发 | 特点 |
|------|------|---------|------|
| **手动执行** | Manual | 点 **Execute Workflow** 按钮 | 边搭边测，迭代调试；**不计配额** |
| **局部执行** | Partial | 在节点上点 **Execute step** | 只跑某个节点 + 为它提供输入的节点 |
| **生产执行** | Production | 发布后由定时器/Webhook/App 事件自动触发 | **计配额**；运行过程不在编辑器里动画展示，去 Executions 列表看 |

### 局部执行（Partial Executions）的常见报错

- **"The destination node is not connected to any trigger"（目标节点没连触发器）**：局部执行也要求工作流有触发器。最简单的解法：加一个 **Manual Trigger（手动触发器）**。
- **"Please execute the whole workflow"（执行数据太大）**：分支特别多的流程做局部执行时可能超限。解法：临时加 **Limit（限制）节点**限制输出，测完再删。

> 💡 **官方提示**：局部执行特别适合「只改了一个节点的逻辑」时——用同样的输入数据重跑这个节点，不用整个流程重来。

### 执行配额（Quota）/ What Counts

付费计划有执行次数上限，**只有生产执行计入配额**：

| 计入配额 | 不计入 |
|---------|--------|
| 定时器触发（每次触发计 1 次，不管成功失败） | 手动执行（编辑器里测试） |
| Webhook 收到请求（含空 body 的请求） | 子工作流执行（只有顶层计一次） |
| 轮询类触发器**找到新数据**时 | 错误工作流（error workflow）执行 |
| — | 轮询没找到数据、被拒绝的请求 |

> 💡 **小白建议**：想省钱就多用手动测试，少发布定时器。测试时用 Pin Data（第 04 章）固定数据，避免反复触发外部 API。

## 2. 执行记录列表 / Execution Lists

n8n 有**两个**执行列表：

| 列表 | 在哪 | 看什么 |
|------|------|--------|
| **Workflow-level（单工作流）** | 工作流顶部的 **Executions** 选项卡 | 当前工作流的历次运行 |
| **All executions（全部）** | 左侧菜单 → Executions | 你所有工作流的运行汇总 |

> ⚠️ 删除工作流会**连同执行历史一起删除**，删前想清楚。

### 筛选执行记录 / Filter

在 Executions 列表点 **Filters**，可以按：

- **Status（状态）**：Failed（失败）/ Running（运行中）/ Success（成功）/ Waiting（等待）
- **Execution start（开始时间）**：只看某段时间
- **Saved custom data（自定义数据）**：用 Code 节点存的自定义标签筛选（见下文）

### 自定义执行数据 / Custom Executions Data

想给执行记录打标签？在 Code 节点里写：

```javascript
// 给执行加自定义数据，之后可以在执行列表里按 key=value 筛选
$execution.customData.set('客户ID', $json.客户ID);
```

### 重试失败的执行 / Retry

执行失败了？在 Executions 列表里找到那条失败记录，点 **Refresh（重试）** 图标即可用相同输入重新跑。

## 3. 调试：拿旧数据修 Bug / Debug & Re-run Past Executions

这是官方推荐的排错流程，强烈建议学会：

1. 打开工作流的 **Executions** 选项卡，找到**失败**的那次执行。
2. 对失败的执行点 **Debug in editor（调试进编辑器）**；对成功的执行点 **Copy to editor（复制到编辑器）**。
3. n8n 会把那次执行的数据**复制进当前工作流，并自动 Pin（固定）在第一个节点**。
4. 现在你改节点、重跑，用的都是**那次真实运行的输入数据**——Bug 会稳定复现，修起来又快又准。

> 💡 **为什么这招好**：生产环境的数据（比如某条诡异的用户输入）最难自己造出来。用真实执行数据调试 = 让 Bug 自己送上门。

## 4. 脏节点 / Dirty Nodes

**脏节点（Dirty Node）**：之前成功执行过、但现在输出被认为「过期不可靠」的节点。表现：**边框变黄 + 黄色三角**（取代绿色对勾）。

**什么会让节点变脏**：

- 插入/删除节点 → 受影响节点之后的第一个节点变脏
- 修改节点参数 → 该节点变脏
- 新增连线 → 连线目标节点变脏
- 停用节点 → 被停用节点之后的第一个节点变脏
- 解除 Pin 数据、修改 Pin 数据 → 相关节点变脏

**怎么消除**：再执行一次这个节点（Execute step 或跑整个工作流）就会恢复绿色。

> 💡 **小白理解**：黄色 = 「你改过东西了，我上次的输出可能对不上现在的配置，重新跑一下」。**别慌，这是正常提示。**

## 5. 实时流式响应 / Stream Real-Time Responses

用 **Chat Trigger（聊天触发器）** 或 **Webhook** 做对话类工作流时，可以开启 **streaming（流式）**，让 AI 回答像 ChatGPT 一样**打字机效果**逐字返回，而不是等全部生成完。

> 官方出处：`understand-executions/stream-real-time-responses.md`。搭配第 12 章 AI 工作流使用。

## 6. 执行数据脱敏 / Execution Data Redaction

团队/企业场景下，可以在**工作流设置**里开启脱敏：

- **Redact production execution data**：生产执行的数据打码（状态、耗时、节点名保留，输入输出隐藏）
- **Redact manual execution data**：手动执行同样打码

适合处理敏感数据（身份证、API Key、客户隐私）的合规场景。开启后执行记录里只能看到脱敏占位符。

## 7. 与执行相关的工作流设置速查 / Related Workflow Settings

在 工作流设置（三个点菜单 → Settings）里：

| 设置 | 作用 |
|------|------|
| **Save failed production executions** | 是否保存失败的生产执行记录 |
| **Save successful production executions** | 是否保存成功的生产执行记录 |
| **Save manual executions** | 是否保存手动执行记录 |
| **Save execution progress** | 是否保存每个节点的中间数据（开启后出错可从断点续跑，但更慢） |
| **Timeout Workflow** | 超时自动取消（可设时/分/秒） |
| **Redact …** | 见第 6 节 |

> 💡 为了**省存储**，正式上线的自动化可以把「保存成功执行」关掉，只留失败记录用于排查。

## 8. 一句话总结 / TL;DR

```
开发期：手动执行 + Execute step + Pin 数据 → 不计费、快速迭代
上线后：去 Executions 列表看运行状态 → 失败记录 Retry / Debug in editor
排错三件套：失败执行 → Debug in editor → 复现 → 修 → 重跑
```
